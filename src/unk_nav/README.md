# unk_nav

未知环境下的**局部反应式导航**核心算法。只用 C++14 标准库；唯一第三方触点 `yaml-cpp` 隔离在 `params_io` 一处（负责 `config/nav_params.yaml` 加载），剔除后核心零依赖，可交叉编译到华为 MDC。

与同工作区的 `rlp_*`（有道路先验的沿路规划）**完全独立**，不复用任何代码。沿路模式只从占据栅格推测可通行方向，不需要显式道路边界或参考线输入。

## 当前实现与版本边界

- `NavCore` 已不调用 A* / `path_smooth`；两种模式（沿路 / 终点）在满足条件时均尝试链式前瞻 + Catmull-Rom 样条，否则生成直线。终点模式链式打分额外加 `goal_align_w` 偏向子目标方向。
- 本次是**可关闭的增量增强**：保留原第一跳选点与直线分支，不是 D*/LPA* 式增量搜索；每周期仍重新规划，仅 EMA 等状态跨周期保存。
- 在实际加载的 YAML 中设 `curve_fit_enable: false`，重新启动导航节点，即回到加入曲线前（`b07b851`）的“单跳选点 + 直线路径”规则。**不会恢复更早的 A* 搜索版本**。
- 新增参数、启用条件、回退边界及已知问题见「二·五」。当前版本仍是实验增强：已发现左弯切向可能造成右侧鼓包，尚未完成 Gazebo 闭环验收。
- 以下 A* 优化路线、历史 demo、平滑模块与性能数据保留作历史参考，不代表当前 `NavCore` 正在使用这些能力。

## 一、核心约束

1. 规划器只使用有限范围的局部占据栅格（车体系 `base_link`），没有全局地图或全局搜索。
2. 终点模式需要全局终点与位姿；终点可在窗口外，`subgoal::project` 负责投影、截断及必要的扇形选点。
3. 沿路模式不需要全局终点或定位来选点；从车头方向扫描局部栅格得到子目标，并可继续接力扫描。
4. 每周期滚动生成局部路径。`occupied` / 越界不可行，`unknown` 乐观放行；当前选点和拟合不会施加 A* 的 `unknown_cost` 软代价。

### 当前能力边界

可根据自由射线选择空隙，但没有局部搜索来保证找到绕障路径，也没有显式道路中心线或路口语义。
凹障碍脱困、横贯道路的封堵处理和路口决策不能由曲线拟合补足；离散几何无碰撞也不等于实际车辆可安全跟踪。
沿路封死场景目前仍有 FSM 回归失败，不能宣称必然稳定停在 RECOVERY/ABORT，见「二·五」。

### 历史 A* 能力记录（不适用于当前主链路）

以下表格与复现命令来自 A* 阶段：只有局部栅格和远处终点时，凹形障碍会造成局部极小。
这些历史绕行结果不能作为当前“子目标 + 直线/曲线”版本的能力保证。

分界线是**凹槽深度与前瞻距离（`lookahead_ratio × perception_range`，默认 4.2 m）的关系**：

| 场景 | 表现 |
|---|---|
| 无障碍 / 凸障碍（横墙、柱子） | ✅ 滚动时域 + 局部 A\* 自行绕开 |
| 凹槽深度 **<** 前瞻 | ✅ A\* 能看到臂端，绕出去（实测绕行比 1.05） |
| 凹槽深度 **>** 前瞻 | ❌ 局部极小 → 无进展判定触发 → RECOVERY → **ABORT** |

复现（凹槽深 6.3 m > 前瞻 4.2 m）：

```bash
./unk_nav_demo --goal 20 0 --obs 10 -1.2 10.3 1.2 \
                          --obs 4 -1.3 10.3 -1.0 \
                          --obs 4  1.0 10.3  1.3
```

**解决凹障碍需要 Bug 式沿轮廓绕行（`BOUNDARY_FOLLOW`）+ 子目标扇形候选展开，
这两项已明确排除在本模块范围外**（决策见文末）。当前行为是主动 ABORT 并把决定权
交回上层，不尝试自己爬出来。

## 一·五、坐标系与栅格数组约定

### base_link 车体系

```
            x（前）
            ↑
            │
   y（左）←─┼─→
            │
            🚗 原点 = 车体几何中心
```

右手系，Z 朝上。yaw = 0 时车头朝 odom 系 X 轴正方向，yaw 逆时针为正。

### 栅格数组布局

`GridMap.data` 是一维数组，行优先（row-major）：

```cpp
data[gy * width + gx]
```

| 索引 | 对应坐标 | 车体方向 | 说明 |
|------|----------|----------|------|
| `gx`（列）增大 | x 增大 | **车前方** | gx=0 是车后方，gx=width-1 是车前方 |
| `gy`（行）增大 | y 增大 | **车左侧** | gy=0 是车右侧，gy=height-1 是车左侧 |

车辆位于数组正中心：`(width/2, height/2)`。

### 栅格原点与坐标变换

```
origin_x = -window_size / 2    ← 栅格 (0,0) 格左下角在 base_link 系的位置
origin_y = -window_size / 2

车体系坐标 → 栅格索引：
  gx = floor((x - origin_x) / resolution)
  gy = floor((y - origin_y) / resolution)

栅格索引 → 格中心车体系坐标：
  x = origin_x + (gx + 0.5) * resolution
  y = origin_y + (gy + 0.5) * resolution
```

### 直观理解（俯视）

```
        gy 增大（车左）
        ↑
        │
        │   ┌────────────────────┐
        │   │                    │
        │   │     data[]         │
        │   │                    │
        │   │        🚗          │  ← 车在中心 (w/2, h/2)
        │   │                    │
        │   │                    │
        │   └────────────────────┘
        │
        └──────────────────────→ gx 增大（车前）
```

### 路径坐标系

`NavResult.path` 中每个点 `(x, y)` 也在 **base_link 系**：
- `path[0]` ≈ `(0, 0)`（车脚下）
- `x > 0` 表示在车前方，`y > 0` 表示在车左侧

### 与 odom 系的关系

| 数据 | 坐标系 | 说明 |
|------|----------|------|
| 栅格 `GridMap` | base_link | 每帧重新生成，车动栅格跟着动 |
| 规划路径 `NavResult.path` | base_link | “从车脚下往前怎么走” |
| 终点 `NavInput.goal` | odom | 远处目标，可在窗口外任意远 |
| 车位姿 `NavInput.vehicle_pose` | odom | 车在世界中的位置和朝向 |
| 控制器输出 `TwistCmd{v,w}` | base_link | v=前向速度，w=逆时针角速度 |

## 二、模块与数据流

```
NavInput{ local_grid(base_link), vehicle_pose, goal, current_speed, speed_valid, now }
   │
   ├─ 1. geom::globalToBase        有效全局终点 → 车体系（沿路选点不依赖它）
   ├─ 2. grid::inflate             障碍按 inflation_radius 膨胀
   │    grid::clearFootprint       仅清膨胀产生的足迹占据，保留 raw 真障碍
   ├─ 3. 子目标
   │    ├─ 终点模式：subgoal::project（投影 / 截断 / 扇形选点）
   │    └─ 沿路模式：road::lookAheadChain 或 road::lookAhead
   ├─ 4. 路径生成
   │    ├─ 沿路且满足开关、链有效、速度门槛：尝试 Catmull-Rom 样条 + 折线碰撞复查
   │    └─ 其他情况或拟合拒绝：车辆原点 → 子目标的直线，k=0
   ├─ 5. speed::limit              制动包络 / 曲率硬门限 + 多项限速
   └─ 6. fsm::BehaviorFsm          IDLE/GO/RECOVERY/ARRIVED/ABORT
   │
NavResult{ path(base_link), recommended_speed, state, emergency_stop, subgoal, kappa_est, chain_hops, chain_hop_count, curve_used, reason }
   └─ PurePursuitController        下游跟踪局部路径
```

| 文件 | 职责 |
|---|---|
| `types.h` | 栅格、路径（弧长 `s` / 几何曲率 `k`）、参数、输入输出及状态类型 |
| `geom_util` | 坐标变换、弧长、重采样、三点曲率、`toPath` |
| `grid_util` | 膨胀、保留 raw 障碍的足迹清理、线段/折线通行检查；另保留供 A* 使用的距离带等工具 |
| `astar` | 保留局部搜索、软代价和 Workspace，当前 `NavCore` 不调用 |
| `path_smooth` | 保留倒角、拉普拉斯松弛及碰撞复查，当前 `NavCore` 不调用 |
| `subgoal` | 终点模式子目标投影、截断及扇形候选评分 |
| `road_follow` | 沿路单跳 / 链式扇形扫描，输出各跳跳点 `hops`、第一跳子目标和诊断曲率 |

## 二·五、接力前瞻（Relay Lookahead, RLA）与可关闭曲线（两种模式共用）

> **命名**：本节这套“看远·走近·接力 n 跳”的规划机制正式名为 **接力前瞻（Relay Lookahead, RLA）**，
> 旧称“链式前瞻”，代码入口 `road::lookAheadChain`。三个动作分属两个时间尺度：
> **帧内**把短步落点接力成 hops 链（一次 `plan()` 内），**帧间**每周期在新车位重跑整条链（滚动重规划，即 MPC 的 receding-horizon 原理）。
> 它的灵魂是把“看多深”（选向视野）与“走多近”（落点步长）**解耦**为两个正交量。

### 保留第一跳，额外估计方向

沿路模式 `follow_road=true` 不依赖全局终点和定位来选择子目标。第一跳仍以车头 `+x` 为中心，
在 ±`road_fan_half_deg` 内扫描，单跳长度 `L = road_lookahead_ratio × perception_range`，
按 `road_free_w·min(d,L)/L + road_align_w·cosθ` 评分。射线每半个栅格分辨率检查一次，遇占据/越界截断。
这只是在选自由空间方向，不保证处于道路中央或能绕过所有障碍。

终点模式 `follow_road=false` 的子目标来自 `subgoal::project()`，但**链式前瞻同样启用**：
`lookAheadChain` 以 `goal_bearing` 透传给 `scanFan`，打分额外加 `goal_align_w × cos(射线−子目标方向)`
偏向目标方向。`goal_align_w=0` 时该加项不生效（沿路模式默认），`>0` 时射线越朝子目标打分越高。

链式版先调用原 `lookAhead` 选出方向 `bearing`（**看多深** `L` 的扇形扫描只用来定方向、防短视），
随后每跳落点只沿选中方向前进**走多近** `= min(road_step_dist, road_step_ratio × L)`（遇障碍再取 `min(走多近, 自由距离)` 提前停）。
在落点放虚拟车、朝向取到达方向，在同一份 base 系栅格中继续扫描接力，最多 `chain_hops` 跳（上限 16）；
没有重采样地图，也没有新增传感器观测。每跳落点依次存入 `hops[]`（`hops[0]=P1=子目标`、`hops[1]=P2`…），供下游样条逐点经过。

- **看多深 ≠ 走多近**：扫描视野 `L` 决定"往哪个方向探"（看得远才不短视），走多近决定"跳点放多密"。
  默认 `road_step_ratio=1.0` → 走多近 `=L` → 落点即射线末端（旧行为，零回归）；调小则跳点变密、曲线更贴走廊。
- **看多深可随速度变（可选）**：`L(v) = min(road_lookahead_ratio×perception_range + lookahead_speed_k·v, perception_range)`，
  即“越快越往远看”（高速提前预见弯道，与曲率限速形成正反馈：直道高速→看远→早发弯道→早降速→看近→跳点密→灵活过弯）。
  `lookahead_speed_k=0`（默认）时 `L` 与速度无关，逐字节零回归。上限夹到 `perception_range`（再远无观测信息）。
  注：因 `走多近 = min(road_step_dist, road_step_ratio×L)`，`L` 变大会使走多近（比例那一路）被动变大，直到 `road_step_dist` 夹住。
- `kappa_est = Σ相邻射线转角 / Σ前一跳前进量`，左正右负。这些长度是射线段长度，不是真实道路弧长。
- `NavCore` 仅对 `kappa_est` 做 EMA（诊断 / 状态文本用）；首次有效链直接初始化。
- 另保留 `tangent_end = β + clamp(δ₂/2, ±30°)`（`β` 第一跳弦向、`δ₂` 第二跳相对转角）作为**纯诊断量**（早期 Hermite 拟合的终点切向），当前样条不再使用它。
- 这是启发式估计，不能把最长自由射线当成真实道路切线，也没有道路曲率精度保证。

### Catmull-Rom 样条与速度规划

拟合改用 `fitSpline`：曲线**精确经过** 车辆原点 → 各跳跳点 `P1→P2→P3→…`（`hops`），不再只画到第一跳末端。
每段切向由相邻跳点差分自动估计（起点切向钉死为车头方向、末点用末段方向外推），逐段三次 Hermite 拼接。
滚动重规划下子目标只是本帧过渡量，让曲线延伸贴合走廊到最远跳点，比"停在 P1"更能预示道路走向；
曲线长度 ≈ `chain_hops × 走多近`，用点数当旋钮调节延伸多远。
按 `path_spacing` 采样，`grid::polylineFree` 复查整条折线，`geom::toPath` 标注弧长 `s` 和几何曲率 `k`。
拟合失败（穿障 / 点太少 / 总长过短）时回退原直线分支。旧的单段 `fitHermite` 仍保留在 `curve_fit` 中，
供参考与独立单测，主链路已不调用它。

速度规划没有直接读取 `kappa_est`：横向加速度、角速度和曲率变化率约束只使用**实际生成路径的 `PathPoint.k`**。
因此有 `kappa=` 不代表正在跟踪曲线，也不代表一定降速；回退直线后 `k=0`，这三项不再限制速度。
制动包络和障碍检查仍运行；`stop_horizon` 仍仅在终点模式接入，沿路子目标截断不直接触发停车视距限速。

### 参数与回退

| 参数 | 默认值 | 实际作用 |
|---|---|---|
| `curve_fit_enable` | `true` | 曲线增强总开关；`false` 跳过接力扫描和拟合，回到单跳 + 直线（两种模式共用）|
| `chain_hops` | `2` | 点数，范围 1..16；1 退化单跳（走直线不拟合）；≥2 跳点作为样条控制点，曲线长 ≈ 跳数 × 走多近 |
| `road_step_dist` | `1e9`（road 配置 `1.5`）| 走多近·固定米 m；每跳落点沿选中方向最多前进这么远 |
| `road_step_ratio` | `1.0`（road 配置 `0.3`）| 走多近·比例 (0,1]，× 看多深 `L`；实际走多近 = `min(road_step_dist, road_step_ratio×L)`。`1.0`=射线末端（旧行为）|
| `lookahead_speed_k` | `0.0` | 看多深·速度增益 s：`L(v)=基准 + k×v`，上限 `perception_range`；`0`=不随速度（零回归）；想高速往远看可试 `2.0~4.0` |
| `chain_ema_alpha` | `0.3` | 配置范围 (0,1]；实现最低夹到 0.001；越小越平滑但滞后，1 表示不混合历史 |
| `goal_align_w` | `0.0`（终点配置 `1.0`）| 终点模式链式打分：子目标方向对齐权重；0=不偏向（沿路默认）；终点模式建议 1.0~2.0 |

回到加入曲线前的沿路行为，编辑实际启动所用的 [`config/nav_params_road.yaml`](config/nav_params_road.yaml)：

```yaml
follow_road: true
curve_fit_enable: false
```

只需关闭总开关，其余三个新增参数可保留。`follow_road: false` 是切换到**终点模式**，不是沿路旧版回退。
两份 YAML 当前都写了 `curve_fit_enable: true`，但 `nav_params.yaml` 默认 `follow_road: false`，不会启用沿路曲线。
旧 YAML 若省略新增键，会使用代码默认值；要保留原沿路行为，应显式写 `false`，不能靠删除该键回退。

- ROS 节点只在启动时通过 `config_file` 加载 YAML，改后需要重启；`rosparam set` 不会修改算法参数。
- C++ 集成方可修改 `NavParams` 并调用 `setParams`；它**不会自动 reset**。前后对照建议重建实例或显式 `reset()`，并使用相同初始状态、输入和其他参数。
- 回退恢复的是 `b07b851` 的单跳/直线路径规则，不是撤销既有车辆运动或 FSM 历史，也不是恢复 A*。
- 没有完成所有输入和字段的逐字节等价测试；新增字段改变了 C++ 类型布局，二进制调用方需同步重新编译。
  若真正换回不认识新参数的旧程序，还需移除四个新增 YAML 键，否则旧加载器会报未知键。

### 自动回退条件

- 子目标无效：不生成路径；不是强行生成直线。
- 只有一跳（`chain_hops=1` 或第二跳失败）：无有效链修正，生成直线。
- 第三跳失败但第二跳成功：保留两跳信息，仍可尝试拟合。
- 速度低于门槛：生成直线，链诊断仍可能非零。
- 弦长小于 `max(path_spacing, 0.001)`、两端切向角差小于 1°，或曲线折线碰撞检查失败：拟合拒绝，生成直线。
- 直线回退只恢复原几何策略；不是任意速度下的动态安全保证。

### 复核发现与尚未验收的部分

1. **终点左切向不保证整段向左弯。** 若第一跳仍为 `P₁=(L,0)`、起点切向为 0、终点切向 `0<θ₁<π`，
   当前公式给出 `y(t)=L·sin(θ₁)·t²(t−1)<0`（0<t<1），内部路径先向右鼓包。
   例如既有测试 `L=4 m、θ₁=0.3 rad` 的最大右偏约 0.175 m。碰撞检查不会拒绝无碰撞的反向鼓包；
   当前测试只验证端点、切向和非零曲率，尚不能证明“提前顺着左弯”。这是待修复问题，本次文档复核未修改算法。
2. **第三跳没有进入控制结果。** 当前拟合仅使用第二跳转角；第三跳仅更新 `kappa_est`，
   后者没有独立接入限速。不能宣称把 `chain_hops` 从 2 调到 3 就会提前降速或更好跟弯。
3. **感知与门控边界。** 宽路、障碍和窗口边缘都会干扰估计；`unknown` 乐观放行不等于看到了遮挡后方。
   仿真无 `/odom` 时车速保持 0，默认 0.5 m/s 门槛使曲线不启用。拟合门控本身未检查 `speed_valid`，
   速度阈值没有滞回，阈值附近路径切换的闭环影响待验证。
4. **状态、采样和性能边界。** 空栅格和模式切换并未统一清理链滤波状态；对照实验应 reset。
   采样间距相对曲率基线过大可能测得零曲率；折线检查不是连续曲线或实际车体扫掠体的严格证明。
   拟合会分配临时 vector，尚未实现新热路径的 Workspace 零 churn，也未实测新增耗时。
5. **离线复跑结果：289 项通过、1 项失败（退出码 1）**。唯一失败为既有测试
   “沿路走廊封死：最终 RECOVERY/ABORT（不谎报 GO）”；新增 43 项断言通过。
   工作区 `catkin_make -j2 -l2` 增量构建通过，但不能据此声称全部功能已验收。
6. **测试覆盖仍有限。** 弯道工具 `makeArcCorridor` 实际生成抛物线而非常曲率圆弧，现曲率断言仅检查符号和宽松量级，
   不是原计划的 ±30% 精度验证。限速测试使用独立合成圆弧，不是拟合路径经 NavCore 的端到端降速证明。
   真实第二跳失败、NavCore 曲线碰撞后回退、全输出开关对照、三跳、滤波重置和新增参数非法值测试仍需补充。
7. **Gazebo 闭环冒烟未执行。** 跟弯方向、速度下降、门槛切换和每周期耗时仍待验收。
   此前计划中的绝对切向限幅 ±60° 实际改成了修正量限幅 ±30°；EMA 也改为滤波相对修正量，不能描述成逐项完全按计划完成。

仿真配置、正确 launch 和对照步骤见 [`unk_nav_sim/README.md`](../unk_nav_sim/README.md) 的「曲线增强与旧版对照」。

## 五、保留的路径平滑模块（非当前主链路）

`path_smooth` 仍保留给独立调用与单测，下述倒角/松弛不是新 Hermite 的后处理，当前 `NavCore` 不调用它。
本节实测值来自旧 A* 路径。

### 历史 A* 路径为什么需要平滑

A\* 出的是栅格阶梯，LOS 拉直后剩尖角折线。直接交给速度规划会有两个后果：拐点曲率极高，
`w = v·κ ≤ w_max` 把速度压死；曲率从 0 阶跃到峰值，`dk/dt ≤ dk_max` 再压一次。

实测横墙绕行（平滑前 → 平滑后）：

| | 平滑前 | 平滑后 |
|---|---|---|
| 最大曲率 | 32.49 /m（转弯半径 3 cm） | **8.11 /m** |
| 过弯最低速 | 0.038 m/s = **17% v_max** | 0.220 m/s = **100% v_max** |

车原本是爬过拐角的，平滑后满速通过。

### 三步做法

1. **拐点圆弧倒角**（`smooth::filletCorners`）
   对每个内角插入与两边相切的圆弧，把曲率上界压到 `1/r`。半径由**目标过弯速度**反解，
   同时满足两条约束：
   ```
   r = max(v_corner / w_max,  v_corner² / a_lat_max)
   ```
   低速差速车由角速度约束决定（0.22/2.84 = 0.0775 m），30 km/h 实车由横向加速度决定
   （8.3²/2.5 = 27.6 m）。换车型只需给出想要的过弯速度，不必手算半径。
   圆弧采样点若碰撞则**半径折半重试**，重试耗尽就保留尖角 —— 宁尖勿撞。

2. **拉普拉斯松弛**（`smooth::laplacian`）
   只做倒角的话，曲率从 0 跳到 `1/r` 仍是阶跃，`dk/dt` 约束照样限速。松弛把阶跃摊开。
   端点固定（起点是车位、终点是子目标，都不许挪），每轮迭代后碰撞复验，撞了就停在上一轮。

3. **最终复验**（`smooth::run`）
   输出前整体再查一次 `polylineFree`，任何意外都退回输入。**宁可交出尖角路径，
   绝不交出撞障路径。**

平滑插在 **LOS 拉直之后、加密采样之前** —— 此时拐点还是显式顶点，倒角才识别得出来。

### 曲率必须按弧长基线测量

这是本轮挖出的最重要的一个缺陷。原来 `toPath` 用**相邻两点**算三点外接圆曲率，于是曲率
随采样密度变化：点距 0.05 m 时 `κ ≈ 565 × 横向偏差`，栅格阶梯的任何微小抖动都被放大成
30+/m 的假曲率。同一条几何路径按 0.02 m 重采样，报出的曲率是 0.05 m 的 2.5 倍 ——
仿真与实车 `path_spacing` 不同时这是致命的。

改为按 `curvature_baseline`（默认 0.30 m，约车辆 0.2~0.5 s 走过的距离）取弧长相距
±baseline/2 的两点来估：

| 输入 | 相邻点估 | 基线估 |
|---|---|---|
| 带 ±0.01 m 抖动的直线 | 13.79 /m（假曲率） | **1.75 /m** |
| R=2 m 真圆弧，spacing 0.05 | 0.50 | 0.50 |
| R=2 m 真圆弧，spacing 0.02 | 0.50 | 0.50（**与密度解耦**） |

端点附近放不下完整基线时，**不能把基线夹成不对称**（一边很短一边很长）：三点外接圆公式
分母是 `ab·bc·ca`，短边会把曲率严重放大，端点处凭空冒出假尖峰（实测 4.91 /m）。
正确做法是只在能放下完整基线的内点区间计算，区间外沿用边界值。

## 七、关键参数

参数以**实际加载的配置文件**为准：终点模式 [`config/nav_params.yaml`](config/nav_params.yaml)，沿路模式 [`config/nav_params_road.yaml`](config/nav_params_road.yaml)。仿真由 `config_file` 指定，离线 demo 由 `--config` 指定；缺省键保留 `types.h::NavParams` 默认值。新增参数须同步字段、`params_io.cpp` 绑定表和相应 YAML，未知键会报错。

当前 `NavCore` 不读取 A* 的 `unknown_cost`、`obstacle_cost_*` 等软代价参数。保留这些配置是为了独立模块使用与单测，不代表调整它们能改变当前规划行为。链式/曲线参数及回退见「二·五」。下面关于搜索、倒角或吸附的说明属于历史模块设计。

### 无量纲化原则

所有与**感知范围**相关的距离都表达为 `perception_range` 的比例：

```
局部窗口  = 1.7  × perception_range     (仿真 20.4 m ← 12 m；实车 51 m ← 30 m)
前瞻距离  = 0.35 × perception_range     (lookahead_ratio)
子目标下限 = 0.10 × perception_range     (subgoal_min_ratio，前瞻的下限保护)
```

换车型 / 换感知源只改 `perception_range` 一个值，整定结果按比例自动迁移。

> **命名沿革**：本参数旧名 `sensor_range`（早期无上游信息时只能自仿真一个激光雷达量程），现上游已直接给出确定的感知栅格地图，故改名 `perception_range`（仅作其尺度基准）。YAML 键已同步，旧键 `sensor_range` 不再被识别。

**但动力学参数不参与这个缩放**：`inflation_radius`、`a_decel_max`、
`a_lat_max`、`w_max` 由车辆本身决定，换感知源不该改变过弯半径。

### 以米为单位、不以格数为单位

`goal_snap_dist`（子目标吸附半径）给的是米，`nav_core` 内部才按当前分辨率换算成格数。
若直接给格数，`resolution` 从 0.05 改到 0.10 时吸附范围会悄悄翻倍。

### 膨胀半径是留给控制器的余量

`inflation_radius = robot_radius + 余量`。这个余量是给**下游控制器跟踪误差**留的，不是
随便给的小数：路径在膨胀栅格上搜出，只保证中心线有 `(inflation_radius - robot_radius)`
的净空。若控制器跟踪误差（尤其纯跟踪在拐点切内角的弦差）超过净空，车会开进膨胀层被
自己的安全边距困死（见「踩过的坑」第 5 条）。要么控制器保证误差不超过净空，要么调大这里。

## 九、历史设计判断（按适用模块阅读）

其中 A* 软代价、路径一致性和平滑条目描述保留模块，不代表当前 `NavCore` 主链路；当前状态以「二、二·五、七」为准。

- **`kappa_max` 默认 0（关闭硬门限）**。差速底盘能原地转向，曲率本身不构成运动学约束；
  栅格直角拐点曲率约 `√2/resolution ≈ 28`，用固定门限硬卡会把所有正常拐弯判死
  （实测：绕行路径已搜到，却被 `kappa_exceeded` 急停至 ABORT）。真正该卡的是
  `w = v·κ ≤ w_max` 与 `a_lat = v²κ ≤ a_lat_max`，这两条是软限速，已实现。
  阿克曼底盘才需要打开 `kappa_max`。
- **障碍距离必须沿线稠密采样**。只在路径顶点查，顶点稀疏时会整段跨过薄障碍，把 `d_obs`
  误判成 inf，制动包络随之失效。
- **`unknown` 乐观放行**。这是「未知环境探索」的正确语义：敢往没探过的地方开，探出障碍
  再滚动重规划。`unknown_cost` 是探索偏好旋钮，>1 偏向已知区。
- **到达判定只判距离、不判航向**。差速底盘原地转向能力充足，强制对齐航向会让车在终点
  附近来回转圈。需要定向停靠时再加参数与判定逻辑，不要留一个"设了但不生效"的旋钮。
- **接口里不留死状态与死参数**。`NavState` 的每个值都真实产生，`NavParams` 的每个字段
  都真实被读取。集成方按枚举写 switch 时不会遇到永不出现的分支，调参时不会拧到空旋钮。
- **平滑的每一步都做碰撞复验，失败即回退**。平滑是「锦上添花」，绝不能为了光滑牺牲安全。
- **真相等的对称只能靠时间信息打破**。轴对称镜像两条路 `f=g+h` 全相等，tie-break（第二关键字 `h`）也相等
  → 无从区分，车每帧左右翻烧饼。解法是把「离上一帧路径的距离」作为**饱和软代价**加进 `g`（`consistency_k`），
  让「沿上帧走」严格更便宜；只加不减 → 欧氏 `h` 仍可采纳，最优性对新代价函数保留。上帧路径存 **odom 系**、
  每帧重投影到 base，车动了才不会滞后错位；软代价有饱和上限 → 原路真被堵死、绕行收益超过它时照样改道，不死抱烂路。

## 十、待验收项与历史问题

当前优先项是「二·五」记录的反向鼓包、门控/滤波边界、回退回归与 Gazebo 闭环验收。
以下保留旧阶段的决策与问题，不能直接作为当前缺陷归因：终点子目标扇形展开已经实现，A* 吸附与路径一致性不在当前主链路；
沿路 FSM 封死用例仍失败，因此旧文“如实 ABORT”不构成所有模式的保证。

### 已明确排除在范围外（历史决策记录）

- **凹形障碍绕行（Bug 式 `BOUNDARY_FOLLOW`）** 与 **`RECOVERY` 实际脱困运动**：
  用户决定暂不考虑。相应地，代码里不留任何"预留但不生效"的接口 ——
  已删除 `NavState::BOUNDARY_FOLLOW` 枚举值、`fan_bearings` / `fan_half_deg` /
  `leave_point_tol` / `block_dist` 四个死参数，以及 `yaw_tolerance`（从未被到达判定读取，
  但文档声称"可开启"）。接口里出现的每一个状态和参数都是真实生效的。

### 待办（按优先级）

1. **实车尺度 + 障碍绕行会 ABORT**
   `--range 30 --goal 200 40 --obs 20 -6 21 6` 复现。原因是 `goal_snap_dist = 0.5 m`
   无法从 1.32 m 厚的膨胀墙里把子目标吸附出来。修法有两条：调大 `goal_snap_dist`
   （最简单，先试这个），或做子目标扇形候选展开（已排除范围）。
2. **换终点 / 换周期时的路径一致性**
   现在每周期独立重规划，可能产生跳变。可加与上一帧路径的偏差惩罚。
3. **`inflate` 的感兴趣区域化**
   实车尺度下它是唯一随栅格总格数线性增长的开销（104 万格约 1 MB 拷贝 + 扫描），
   目前占比可接受。
4. ~~**ROS 节点壳 + Gazebo 仿真**~~ —— 基础已就位（`unk_nav_sim`：`localization_node` + `grid_node`
   + `nav_node`；沿路模式有 `road_world.world` / `road_follow.launch`）。下一步：等实车接口定义后
   做集成调试；仿真侧可扩展更多道路场景或接入外部感知。

### 已知的行为特性（不是 bug，但集成方必须知道）

- **无进展判定用"朝终点推进量"而非"位移量"**（`behavior_fsm.cpp` 有完整论证）。
  位移量判定有致命盲区：车在凹槽里横向振荡时位移不小，判定永远沉默，模块会持续
  上报 `GO` + 满速。实测深凹槽场景旧实现振荡 280 秒全程报 GO —— 不是报错，是谎报
  健康。改成推进量棘轮后如实 ABORT。代价：`stuck_dist` 必须小于绕行期间每
  `stuck_time` 的正常推进量，否则必要的绕行会被误判（默认 0.05 m / 3 s，而
  `v_max × stuck_time = 0.66 m`，余量充足）。
- **`RECOVERY` 不产生任何运动**，只是上报一个状态；连续 3 次即 `ABORT`。
  上层收到 `ABORT` 需要自己决策（换终点 / 人工接管 / 停车）。
